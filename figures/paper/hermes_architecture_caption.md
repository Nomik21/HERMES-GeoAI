**Figure 4.1. Full HERMES system architecture.** HERMES processes five input configurations through a sequential CrewAI-orchestrated pipeline composed of four single-responsibility agents: GeoPerception, GeoImageRestoration, GeoDamageAnalysis and GeoReasoning. Each agent communicates through schema-validated persisted artefacts, enabling modular inspection and component-level evaluation. The evaluation layer consumes the intermediate JSON outputs and final reports to score hazard classification, input-mode recognition, severity estimation, object-indicator detection, internal consistency and strict operational quality.

---

*Supplementary implementation note (not part of the caption above — for the thesis text or a footnote, if useful):* GeoImageRestoration is invoked conditionally and is optional/guarded — it only runs when GeoPerception flags a restoration need, and its Gemini-based planner only selects which deterministic OpenCV/scikit-image tool to apply, never generating pixels itself. GeoDamageAnalysis routes each case to one of four implemented scenarios (`pre_post_svi`, `cross_view_svi_rsi`, `wildfire_building`, `object_detection`). The three intermediate JSON artefacts are written to `outputs/intermediate/<case_id>_{gpa,gira,gdaa}.json` (`pipeline_state.py`). The final report is saved as JSON, Markdown and HTML; in the current codebase these are written under a scenario-specific subfolder (`outputs/Scenarios/<scenario>/reports/<scenario>__<case_id>_report.{json,md,html}`) rather than directly under `outputs/`, so the simplified `outputs/<case_id>.json/.md/.html` shown in the figure should be read as an illustrative, shortened form of that path rather than the literal one.
